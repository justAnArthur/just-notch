# AGENTS.md — just-notch

A modular macOS notch app. A thin Swift host owns the window and system services; everything visible is React + `@justanarthur/modo-ui` in ONE transparent WKWebView. Plugins add behavior and UI.

## layout

- `packages/bridge-schema` — the host ⇄ web contract (methods, topics, events, manifest). Source of truth; the Swift host mirrors it as Codable by hand. Change both in the same commit.
- `packages/sdk` — `@just-notch/sdk`: `definePlugin`, `PluginContext`, hooks. Shared at runtime through the import map.
- `packages/runtime` — the React app inside the web view: island shell (a sheet with two snaps: fitted to the tab, then tall), activity manager, plugin loader, the settings page (a tab of the island on its tall snap), mock host (runs in any browser).
- `packages/runtime/src/host/swift-host.ts` — `createSwiftHost()`: the just-apps platform `Host` (`@just-apps/host-contract`, kind `swift`) over the bridge, as the runtime. The mock host backs it in a browser. Clipboard text, notifications (`notifications.send`), global shortcuts (Carbon hot keys, no Accessibility; released with the page), deep links (`justnotch://`), opening a file with a named app and the updater (`updater.check` / `updater.install`, Sparkle) all go through the bridge.
- `packages/cli` — `notch create | dev | build | pack | install | check` for plugins. At the root: `bun run notch <command> --cwd plugins/<id>` (not `bunx notch`, an unrelated npm package).
- `plugins/<id>` — default plugins, written only against the public SDK.
- `library/<id>` — optional plugins: same rules, a workspace too, but not bundled into the app (`copy-web.sh` copies `plugins/*` only). The dev server serves them with `builtIn: false`; `bun run build:library` builds them. Each is released on its own (see library plugins).
- `apps/macos` — Swift 6, macOS 14+, XcodeGen `project.yml`. `Packages/NotchServices` — system services as a SwiftPM package (protocol in `Service.swift`).
- `assets/brand` — brand masters (logo, app icon, menu bar glyph, lockups, wordmark), text outlined. `apps/macos/scripts/make-icon.sh` renders `icon-1024.png` into the `AppIcon` set; the status item's `StatusIcon` PDF comes from `menubar.svg` (`rsvg-convert -f pdf -d 72 -p 72`).
- `site` — the website (Vite + modo-ui, its hero island from `@justanarthur/modo-ui-notch`), deployed to GitHub Pages by `pages.yml`. Three pages (`index.html`, `changelog/`, `developers/`), each prerendered at build (`src/entry-server.tsx` → `scripts/prerender.ts`) and hydrated by `src/boot.tsx`; the entry script loads on the first interaction or 1.5 s after load (`vite.config.ts`), which keeps Lighthouse at 99–100. `scripts/changelog.ts` writes `public/changelog.json` from the app's releases before the build (gitignored, bundled into the changelog page).

## platform

just-notch is `apps/notch` in the just-apps monorepo and builds only inside a just-apps checkout: the runtime depends on `@just-apps/host-contract` by path (`file:`, relative to `apps/notch`). CI checks out just-apps around this repo (secret `PLATFORM_TOKEN`).

## runtime conventions (shared by runtime, CLI and plugins)

- The page is served from `notch://app/` (prod) or the Vite dev server (dev). Plugins live under `<origin>/plugins/<id>/` (same origin, so ES modules load without CORS).
- Shared modules via import map, emitted by the runtime build to `shared/`: `react`, `react/jsx-runtime`, `react-dom`, `react-dom/client`, `motion`, `motion/react`, `@justanarthur/modo-ui`, `@justanarthur/modo-ui-notch`, `@just-notch/sdk`. Plugin builds mark exactly these external. Plugins import modo-ui and the kit from their barrels only.
- Plugin UI comes from the notch kit (`@justanarthur/modo-ui-notch`): a plugin maps host topics onto a kit block and its parts (`.Leading` / `.Trailing` / `.Minimal` / flash). New visuals go into the kit in the modo repo, not into a plugin.
- Plugin API version: bridge-schema `API_VERSION` (mirrored as `Semver.apiVersion` in NotchServices `Plugins/SemverRange.swift`), not the app version: minor for an addition to the bridge or the SDK, major for a break. User and library plugins whose `engines.notch` doesn't admit it are listed with `incompatible` and never loaded; built-in plugins ship with the app and aren't checked. `satisfies` / `compareVersions` exist in both languages and run `packages/bridge-schema/test/semver-cases.json`. `notch create` scaffolds `^API_VERSION`.
- A plugin folder: `manifest.json` (bridge-schema `PluginManifest`), `dist/index.js` (default export = `definePlugin(...)`), optional `dist/index.css` (UnoCSS with `@justanarthur/modo-ui/unocss` preset over the plugin's sources).
- The island is always on true black: the `--island` token (runtime `tokens/island.css`) and the `.island` scope pin dark and lift the modo-ui surface ladder from it.

## net and secrets

- `net`: `ctx.fetch(url, { method, headers, body | json, timeoutMs })` resolves with a real `Response` (any status) from the host's URLSession (`NotchServices/Plugins/HTTPProxy.swift`): no cookies, cache or CORS, `User-Agent: JustNotch/<version>`, at most 6 in flight per plugin, responses over 5 MiB reject. `https:` only, `http:` for local hosts.
- Hosts allowlist: the manifest's `hosts` (`api.github.com`, `*.youtrack.cloud` for subdomains only, `host:8443`; lowercase, no scheme or path; a wildcard needs two labels after `*.`) plus exact hosts the user granted through `ctx.net.requestHost(url, reason?)`, a native dialog (UserDefaults `plugins.hosts`; a denial sticks for the session). Every redirect hop is re-checked; `Authorization` is dropped once a redirect leaves the original host. One matcher in two languages: bridge-schema `hostAllowed` and `HostPattern.swift`, both run `packages/bridge-schema/test/host-cases.json`.
- `secrets`: `ctx.secrets.get / set(key, value | null) / subscribe`, `useSecret(key)`. All plugins' secrets are ONE Keychain generic-password item (service `com.justanarthur.justnotch.secrets`, account `plugins`) holding `{pluginId: {key: value}}`: the app isn't sandboxed, so it uses the legacy file keychain, whose access lists are bound to the designated requirement — once per item, so one item. Releases since the self-signed certificate keep it across updates; ad-hoc builds (local, or up to 1.2.x) have a cdhash requirement and prompt again after every update. `secrets.changed` never carries the value (unlike `storage.changed`, which every web view receives with it). Never put tokens in `ctx.storage`.
- The runtime (`plugin: 'runtime'`) skips permission checks, so the host refuses it `net.fetch`, `net.requestHost`, `net.hosts` and `secrets.*` (`PLUGIN_ONLY`).
- Isolation caveat: plugins share one JS realm and the `plugin` id on a bridge request is self-asserted, so permissions and host lists stop mistakes, not hostile code. Install only plugins you trust.
- Dev: the mock host keeps secrets and grants in localStorage (`notch:mock:secret:<id>:<key>`, `window.confirm`) and sends `net.fetch` through the dev server's `/__notch/net` (Node fetch; loopback, same-origin callers only; only to the calling plugin's manifest hosts or exact grants).

## styling

modo-ui rules apply (see its AGENTS.md / DESIGN.md in github.com/justAnArthur/modo, `ui/`): tokens only through its utilities (`bg-surface-N`, `text-<role>`, `text-muted-foreground`, `bg-hover`, `spring.*` from motion tiers), no arbitrary color/type/radius/shadow/motion values, no inline style for visuals. Arbitrary values are fine for layout geometry. Missing a step? Add a token in `tokens/*.css`.

## code style

Sparse: smallest correct code, trust the types, early returns, no comments except a non-obvious why. Default exports for components. `interface` over `type` for objects.

## checks

- `bun run check` (typecheck all workspaces)

## releases

- One versioned product: the app, versioned in the root `package.json` (`just-notch`, tags `just-notch@x.y.z`). The workspace packages and plugins are private and ship inside the app. Library plugins are the exception, see below.
- `bump-version.yml` (from just-github-actions-n-workflows, see `.github/AGENTS.md`) bumps on push to `main` from Conventional Commits whose scope is one of the root `properties.gitCommitScopeRelatedNames` (`app`, `macos`, `host`, `services`, `runtime`, `island`, `sdk`, `cli`, `bridge-schema`, `plugins`, or a plugin id): `feat`/`perf` minor, `fix`/`refactor`/… patch; `!` after the type or scope (`feat!:`, `fix(runtime)!:`) or a `BREAKING CHANGE:` footer major, on `0.x` too (`0.4.3` → `1.0.0`). Unscoped commits (and `[skip bump]`) don't release.
- A new tag starts `release-on-tag.yml` (GitHub release with notes) and `build-macos-on-tag.yml` (builds the app on macOS with `MARKETING_VERSION` from the tag, attaches `JustNotch-x.y.z.zip` and a stable `JustNotch.zip`, which the site's Download button links through `releases/latest/download/`).
- Updates: Sparkle 2 (SwiftPM, `apps/macos/JustNotch/App/Updater.swift`) reads `releases/latest/download/appcast.xml`. The tag build signs the zip with the EdDSA private key from the `SPARKLE_PRIVATE_KEY` secret and attaches an appcast naming that release (`apps/macos/scripts/appcast.sh`); without the secret it warns and attaches none. The public key is `SPARKLE_PUBLIC_KEY` in `project.yml`; a Release build fails while it's the placeholder, other builds run without updates. Sparkle (`SUUpdateValidator`) accepts an app update when the archive's EdDSA signature matches the old app's key OR the code signatures match, so the ad-hoc → self-signed switch needs no special step. CFBundleVersion is `major*10000 + minor*100 + patch`. One-time setup: `generate_keys` (key in your login keychain), its public key into `project.yml`, `generate_keys -x <file>` → `gh secret set SPARKLE_PRIVATE_KEY -R justAnArthur/just-notch < <file>`, delete the file. Keep the Sparkle version in `project.yml` and `SPARKLE_VERSION` in the workflow in step.
- Code signing: the tag build signs with a long-lived self-signed certificate, "Just Notch Self-Signed" (`apps/macos/scripts/make-signing-cert.sh`, run once by the owner; secrets `MACOS_CERT_P12` = base64 `.p12`, `MACOS_CERT_PASSWORD`), from a temporary keychain deleted after the job; `apps/macos/scripts/sign-nested.sh` re-signs Sparkle's helpers, framework and the app with it. The designated requirement becomes `identifier "com.justanarthur.justnotch" and certificate leaf = H"<sha1>"`, the same for every release, so TCC grants (Calendar, Location, Automation, folders, Bluetooth) and Keychain ACLs survive updates; the build fails if it's still cdhash-based. Without the secret it warns and signs ad hoc. Users coming from 1.2.x (ad hoc) grant permissions one last time. Keep `disable-library-validation`: there is still no Team ID, and dyld refuses Sparkle.framework without it. Never replace the certificate: that resets every user's permissions. Clean long-term fix: Developer ID + notarization.
- Toolkit workflow files are managed by its CLI (`npx @justanarthur/just-github-actions-n-workflows-cli update`); don't edit `bump-version.yml` / `release-on-tag.yml` by hand. `ci.yml` and `build-macos-on-tag.yml` are this repo's own.

## library plugins

- Scaffold: `bun run notch create <id> --library` (= `--dir library`): `library/<id>` with `package.json` `@just-notch/plugin-<id>`, `version` 0.1.0 and `properties.gitCommitScopeRelatedNames: "<id>"`. Then `bun install`, `bun run notch check --cwd library/<id>`; try it in the real app with `bun run notch install [--watch] --cwd library/<id>` (copies into `~/Library/Application Support/JustNotch/Plugins/<id>`).
- Scope: commit as `feat(<id>): …`. The id is the plugin's own scope and must NOT be in the root list (that would release the app too); `notch check` errors on that, on a missing scope property and on an id also in `plugins/`.
- Version: `package.json` `version` is the source of truth (the bump bot edits it); `notch pack` stamps it into the packed manifest and `notch check` warns when `manifest.json` differs.
- Release flow: `bump-version.yml` bumps `library/<id>/package.json`, tags `@just-notch/plugin-<id>@x.y.z` and dispatches the tag workflows. `release-on-tag.yml` creates the release; `build-library-on-tag.yml` runs `notch pack --json` (reproducible: same sources, same sha256), attaches `<id>-x.y.z.notchplugin` and its `.sha256`, re-marks the newest stable `just-notch@*` release Latest, then starts `pages.yml`.
- Latest caveat: `release-on-tag.yml` (toolkit-owned) marks every new release Latest, and Sparkle's feed and the site's Download button go through `releases/latest/download/`. `build-library-on-tag.yml` puts Latest back on the app; if it fails or another non-app release lands after it, fix it by hand: `gh release edit just-notch@x.y.z --latest`.
- Catalog: `https://justanarthur.github.io/just-notch/library/index.json`, bridge-schema `LibraryCatalog` (`schema: 1`, only each plugin's latest version, absolute URLs; `signature` reserved). `pages.yml` writes it with `site/scripts/library-catalog.ts` (`bun run catalog` in `site`, tests `bun run test`): per `library/<id>`, the newest stable release with a `.notchplugin`, its size and SHA-256 (checked against the `.sha256`), the manifest packed inside it (never HEAD), the packed icon and `assets/screenshots/*.png` copied to `site/public/library/<id>/` (gitignored); `--local` packs `library/*` instead, for a preview. The site's Library section reads the same file. The host caches it in memory and in `~/Library/Application Support/JustNotch/Library/catalog.json` and serves it as `library.catalog` (offline: the cached one).
- Install (`apps/macos/JustNotch/Library/LibraryStore.swift`): `library.install` takes only an id; URL, size and hash come from the catalog, never from the page. The download must start with `https://github.com/justAnArthur/just-notch/releases/download/`, match the entry's size and SHA-256, unzip through NotchServices `PluginArchive` (stored/deflate only, safe names, only `manifest.json`, `dist/**` and the icon, ≤ 10 MB, ≤ 500 files, ≤ 100× per entry, exclusive creates, tree re-checked) into `Staging/<uuid>`, carry a manifest whose id, version, permissions and hosts equal the entry's, not shadow a built-in id, and satisfy `engines.notch`. Then a native NSAlert (`Library/Consent.swift`: everything on install, only what's new on update; the web UI can be spoofed) and `FileManager.replaceItemAt` into `Plugins/<id>`; `Library/installed.json` records `{id: {version, sha256, installedAt}}`, which makes the plugin's `source` `library`. `library.progress` events follow each step.
- Uninstall: `library.uninstall` asks natively and moves the folder to the Trash; the dialog's unchecked “Also delete its saved data and keychain items” also drops its secrets, `Storage/<id>.json`, host grants and on/off state. Both reject with `cancelled` when the user says no.
- Settings → Library (`packages/runtime/src/settings/library.tsx`, the kit's `LibraryListing`): states from the catalog, the installed list and `HostInfo.apiVersion` (`library-state.ts`), `library.progress` for the bar, `permissionInfo` in plain words for every `Permission` (keep it in step with `Consent.swift`). The sidebar row counts updates; the Plugins list badges Incompatible / Update / Library and offers Uninstall for user and library plugins; a plugin's settings page lists the hosts the user granted it, with Revoke.
- Deep link: `justnotch://library` opens Settings → Library, `justnotch://library/<id>` that plugin's page (`settings/deep-link.ts`). A link only shows; installing always takes the user's click and the native dialog.
- Debug only: `NOTCH_LIBRARY_URL` (or the `library.url` default) points at another catalog, whose origin downloads may then come from too; `NOTCH_CONSENT_AUTO=accept|accept-delete|deny` answers the install and uninstall dialogs for scripted tests. Both are compiled out of Release.
- Mock host: `library.catalog` is built from the dev-served `library/*` manifests plus an incompatible `linear`; installs and uninstalls flip the list (localStorage `notch:mock:library`) with progress events and `window.confirm`. `__notchMock.libraryUpdate(id)` lists a newer patch, `__notchMock.libraryOffline()` fails the catalog.
